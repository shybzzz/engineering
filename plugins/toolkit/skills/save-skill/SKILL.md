# Збереження скіла в особистий маркетплейс

Маркетплейс користувача — git-репозиторій `MARKETPLACE_REPO` (див. Конфігурацію нижче). Скіли живуть у плагіні `toolkit`: `plugins/toolkit/skills/<назва-скіла>/SKILL.md`.

## Конфігурація

- MARKETPLACE_REPO: `https://github.com/shybzzz/engineering`
- Локальна копія (якщо є): `~/engineering`
- Плагін для скілів: `toolkit`

## Процедура

1. **Знайди репозиторій.** Перевір, чи існує локальна копія (`~/engineering`). Якщо так — `git pull`. Якщо ні — клонуй `MARKETPLACE_REPO` у `~/engineering`. Якщо клонування не вдалося (немає доступу/мережі) — зупинись і скажи користувачу, що саме не вийшло.

2. **Сформулюй скіл.** З контексту розмови визнач, що саме треба зберегти: процедуру, знання, конвенції. Запитай у користувача лише те, чого бракує (назва, тригери). Назва — kebab-case, без слів "claude" та "anthropic", до 64 символів.

2a. **Зроби скіл агностичним до проєкту — ЗАВЖДИ, навіть якщо користувач цього не просив.** Скіл у маркетплейсі має працювати в будь-якому іншому проєкті, тому прибери або перефразуй усе специфічне для поточного (чи будь-якого іншого) проєкту:
   - назви проєктів, досліджень, замовників, пристроїв, Confluence-просторів, id сторінок, URL сайтів → плейсхолдери (`<site>`, `<space>`, `<id>`, «проєкт») або загальні формулювання;
   - шляхи до папок, скриптів, файлів даних → узагальнені (`img/<topic>/`, `python <script>.py`, «data root проєкту»);
   - перелік того, що вже зроблено в проєкті, дати, стан портування, списки перевірених джерел/DOI → видалити; замість них — правило «якщо проєкт веде такий список/стан, використовуй його»;
   - правила, що випливають із конкретного проєкту, але корисні загалом (термінологія, формат, перевірки) — залишити, сформулювавши без прив'язки.
   Після написання перевір grep-ом за назвами проєкту, id, абсолютними шляхами; жодного збігу не має залишитись.

3. **Створи/онови файл** `plugins/toolkit/skills/<назва>/SKILL.md`:
   - frontmatter: `name` (= назва папки) і `description` — одне-два речення, КОЛИ використовувати скіл, із конкретними тригер-фразами користувача (саме description вирішує, чи спрацює скіл);
   - тіло: покрокові інструкції, приклади, обмеження. Пиши для моделі, не для людини: імперативно, конкретно, без води.
   - Допоміжні файли (скрипти, шаблони) клади поруч у ту ж папку і посилайся на них відносними шляхами.

3a. **Перепиши скіл-джерело в проєкті — ЗАВЖДИ**, якщо скіл зберігається з наявного проєктного файлу (`<проєкт>/.claude/skills/<назва>/SKILL.md` або подібного). Джерело НЕ має дублювати загальний текст. Його нова структура:
   - frontmatter: той самий `name`; `description` — коротко: «Проєктні доповнення до `toolkit:<назва>`: …» + тригери, специфічні для проєкту;
   - перший абзац тіла: «Загальні правила — у скілі маркетплейсу `toolkit:<назва>`; застосовуй його разом із цим файлом. Тут — лише специфіка проєкту.»;
   - далі — ВСЕ, що було прибрано на кроці 2a: шляхи, id сторінок, назви досліджень і їхній стан, перевірені DOI, конкретні скрипти, винятки з загальних правил для цього проєкту. Нічого з проєктної інформації не має загубитись — вона переїжджає сюди.
   Якщо джерела немає (скіл формулюється з розмови), але в розмові є проєктні деталі, які прибрано, — створи такий файл у `<проєкт>/.claude/skills/<назва>/SKILL.md` і повідом про це користувача.

4. **Підніми версію плагіна** у `plugins/toolkit/.claude-plugin/plugin.json` (patch для правок, minor для нового скіла).

4a. **Онови README.md у корені репозиторію — ЗАВЖДИ**, при кожному додаванні, перейменуванні, суттєвій зміні призначення чи видаленні скіла: дерево в розділі «Структура» і рядок у таблиці «Скіли» (назва, тригери, що робить). README має відображати фактичний стан папки `plugins/toolkit/skills/`.

5. **Перевір**, якщо доступний CLI: `claude plugin validate ~/engineering`. Якщо CLI немає — перевір вручну: валідний JSON, frontmatter з name/description, name збігається з назвою папки.

6. **Закоміть і запуш:**
   ```bash
   cd ~/engineering
   git add -A
   git commit -m "Add/update skill: <назва>"
   git push
   ```
   Якщо push відхилено — `git pull --rebase` і повтори. Ніколи не роби force push.

7. **Повідом користувача:** назва скіла, що він робить, що саме узагальнено і куди переїхала проєктна специфіка (шлях до скіла-джерела), і нагадай, що на інших машинах оновлення підтягується через `/plugin marketplace update engineering` (локально зміни активуються після `/reload-plugins` або нової сесії).

## Оновлення та видалення

- Оновлення: та сама процедура, редагуй наявний SKILL.md.
- Видалення: тільки на пряме прохання користувача; видали папку скіла, прибери його з README, підніми версію, закоміть з повідомленням "Remove skill: <назва>".
